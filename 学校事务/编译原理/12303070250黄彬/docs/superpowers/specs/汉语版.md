**编译器流水线 GUI 设计**

**目标 (Goal)**

围绕现有的算法代码，构建一个集成的编译器课程设计应用程序。该程序支持当前语法分析器、语义分析器和中间代码生成器已经涵盖的类 C 语言子集：

- `int`、`float`、`char`、`void`、`const`
    
- 变量和常量声明
    
- 函数声明和定义
    
- `if`/`else`、`while`、`do-while`、`for`
    
- `break`、`continue`、`return`
    
- 函数调用
    
- 算术、关系、相等、逻辑、一元和赋值表达式
    

最终的应用程序既应作为一个可演示的 Tkinter 桌面应用程序运行，也应作为用于课程检查的文件输出工具运行。

**架构 (Architecture)**

现有的实验文件（`exp2.py`、`exp3.py` 和 `exp4.py`）将保留作为参考资料。新代码应被组织成一个小型包：

- `compiler/token.py`：共享的 token 和诊断数据类。
    
- `compiler/ast.py`：共享的 AST（抽象语法树）节点、AST 格式化以及 AST 转换辅助函数。
    
- `compiler/lexer.py`：全新的词法分析器，用于将源代码转换为 token 列表。
    
- `compiler/parser.py`：重构 `exp2.py` 中的可用逻辑，使其消费共享的 token 并生成共享的 AST。
    
- `compiler/semantic.py`：重构 `exp3.py` 中的可用逻辑，使其直接分析共享的 AST。
    
- `compiler/ir.py`：重构 `exp4.py` 中的可用逻辑，使其根据共享的 AST 生成四元式（quadruples）。
    
- `compiler/pipeline.py`：一个公开的流水线函数，用于运行编译器的所有阶段并返回结构化的结果。
    
- `app.py`：Tkinter GUI 的入口点。
    

这种架构避免了当前存在的不匹配问题：`exp2.py` 输出文本形式的 AST，`exp3.py` 重新解析文本形式的 AST，而 `exp4.py` 则使用了一个独立的微型解析器。

**数据流 (Data Flow)**

- 用户在 GUI 中输入源代码或打开一个源文件。
    
- **词法分析器 (Lexer)** 生成 token 和词法诊断信息。
    
- **语法分析器 (Parser)** 消费 token 并生成共享的 AST 以及语法诊断信息。
    
- **语义分析器 (SemanticAnalyzer)** 消费共享的 AST 并生成语义诊断信息和符号表。
    
- **四元式生成器 (QuadGenerator)** 消费共享的 AST 并生成四元式。
    
- **流水线结果 (PipelineResult)** 暴露出所有阶段的输出，以供 GUI 显示和文件导出。
    
- 如果前面的阶段报告了阻塞性错误，后续阶段仍应显示那些可以安全计算出的输出。例如，当语法分析失败时，仍应显示 token 的输出。
    

**GUI 设计 (GUI Design)**

Tkinter 窗口的设计应优先考虑课程演示：

- **左侧：** 源代码编辑器，包含打开、保存、运行、清除和导出按钮。
    
- **右侧：** 笔记本选项卡（标签页），分别用于显示 token、AST、语义错误、常量、变量、函数和四元式。
    
- **底部状态区：** 当前文件路径、运行状态和摘要计数。
    

GUI 不应需要额外的第三方依赖。它应使用 Python 标准库中的 `tkinter` 和 `ttk` 模块。

**文件输出 (File Output)**

每次成功运行都应创建或刷新一个 `outputs/` 目录，其中包含：

- `tokens.txt`
    
- `ast.txt`
    
- `semantic_errors.txt`
    
- `const.txt`
    
- `var.txt`
    
- `function.txt`
    
- `quads.txt`
    

输出格式应与现有的实验文件保持相近，以便以前的算法行为仍然可以被识别出来。

**错误处理 (Error Handling)**

应用程序应收集诊断信息，而不是在遇到格式错误的输入时直接崩溃。诊断信息应至少包含行号、所属阶段、代码或类别，以及提示消息。GUI 的选项卡应以纯文本表格的形式显示这些诊断信息。

语义分析器应尽可能保留现有的错误码样式：

- **301:** 重复声明 (duplicate declaration)
    
- **302:** 未声明的标识符 (undeclared identifier)
    
- **303:** 重复的函数声明或定义 (duplicate function declaration or definition)
    
- **304:** 未定义的函数 (undefined function)
    
- **305:** 函数参数数量不匹配 (function argument count mismatch)
    
- **306:** 函数参数类型不匹配 (function argument type mismatch)
    
- **307:** 返回类型不匹配或缺少返回值 (return type mismatch or missing return)
    
- **308:** 非法的 break (illegal break)
    
- **309:** 对常量赋值 (assignment to const)
    
- **310:** 表达式类型不匹配 (expression type mismatch)
    

**测试 (Testing)**

测试应侧重于集成行为：

- 词法分析器能正确识别关键字、标识符、字面量、运算符、分隔符、注释和行号。
    
- 语法分析器能为声明、函数、循环、分支、调用和表达式构建正确的 AST。
    
- 语义分析器能在具有代表性的无效程序上报告出已知的错误码。
    
- 中间代码生成器能为赋值、表达式、分支、循环、调用和返回生成正确的四元式。
    
- 流水线能将所有预期的文件写入 `outputs/` 目录下。
    

如果代码库没有现成的测试环境，初版实现可以使用简短的示例源码字符串和脚本级别的检查，而无需引入大型的测试框架。

**非目标 (Non-Goals)**

本设计不增加数组、switch/case/default 分支、标准库 I/O、预处理指令、指针语法、结构体语法或完整的 C 语言语法兼容性。这些可以在集成的流水线稳定之后，作为后续的扩展功能来实现。
